# Описание сайта и текущей логики поиска

Описание составлено 27 сентября 2026 года по исходному коду проекта. Это аудит реализации, без повторной сетевой проверки доступности поставщиков. Статусы в реестре отражают ранее зафиксированные условия доступа и не являются результатом сегодняшней проверки.

## 1. Назначение

Global Travel Optimizer — прототип конструктора семейной поездки. Его задача — сравнивать российский пакетный тур, зарубежный пакет с дополнительным перелётом до аэропорта старта, сборку через B2B-поставщиков, самостоятельную розничную сборку и чартер с отелем.

Сравнение должно учитывать полную стоимость семьи, гибкие даты, разную длительность отдыха отдельных групп, документы, пересадки, проживание и обязательные расходы. Сейчас полный сценарий реализован преимущественно как синтетическая демонстрация. Получение реальной комплексной цены из API ещё не соединено в единый рабочий поиск.

## 2. Что вводит пользователь

- Город и аэропорты вылета, радиус соседних аэропортов.
- Самый ранний и самый поздний вылет, крайний возврат, диапазон ночей.
- Количество взрослых и возраст каждого ребёнка.
- При разделении семьи: взрослые и дети в каждой группе, диапазон ночей каждой группы. Демо предполагает общий вылет и отдельные возвращения.
- Гражданство, тип и срок действия паспорта, наличие виз, разрешение eVisa и visa on arrival, допустимые визовые расходы и сроки.
- Страны, семейный бюджет, лимит на человека, питание.
- Номера, звёздность, рейтинг, семейное размещение и удобства.
- Пляж, вход в воду, риф, приливы, температура и погода.
- Прямые рейсы, пересадки, багаж, длительность, ночные и самостоятельные пересадки.
- Веса цены, погоды, пляжа, удобства дороги и отеля.

Блок «ИСТОЧНИКИ ПОИСКА» включает туроператоров, B2B и розничную сборку. Туроператоры разделены на российских и зарубежных. Для зарубежного пакета задаются разрешение позиционирования, максимальная цена и длительность дополнительного перелёта, ночёвка, self-transfer и минимальный запас времени — по умолчанию 12 часов.

## 3. Три режима сайта

### Демо

Работает в браузере через `frontend/lib/search.ts`, функцию `searchMock`. Для получения карточек внешние API не вызываются.

Используются встроенные направления, вымышленные отели, условные погодные и пляжные характеристики, условные цены. Поддерживаемая модель ограничена вылетом из Москвы и обычным паспортом РФ. Алгоритм перебирает даты и длительности групп, применяет фильтры и оставляет минимальную модель по каждой комбинации направления, типа источника и gateway.

Карточки сортируются по полной синтетической стоимости, при равенстве — по оценке соответствия. Можно открыть состав цены, сохранить карточку в localStorage и сравнить до четырёх вариантов. Реального бронирования нет.

**Важно:** демо-фильтр виз не вызывает серверный VisaRuleEngine. Он использует локальные условные категории и исключает немецкий gateway без Шенгена. Показанная карточка со статусом CHECK не подтверждает право въезда. В модели маршрута отображается преимущественно путь туда; полноценная временная шкала обоих направлений ещё не формируется из расписаний.

### Реальный поиск

Браузер отправляет `filters`, `party` и `source_settings` на `POST /api/search`. Адрес backend берётся из `NEXT_PUBLIC_API_URL`, по умолчанию `http://127.0.0.1:8000`.

Endpoint проверяет часть входных данных, формирует список включённых веток и оценивает gateway через VisaRuleEngine. Приоритет: TR/IST, AE/DXB, QA/DOH, OM/MCT, CN/PEK, GE/TBS, AM/EVN, AZ/GYD, KZ/ALA, UZ/TAS, RS/BEG.

Сейчас у двигателя нет подключённого набора актуальных визовых правил. Поэтому gateway не получает разрешение, а зарубежная ветка помечается `VISA_EVIDENCE_REQUIRED`.

**Endpoint не запускает запросы тарифов к перечисленным поставщикам.** Поле `parallel: true` описывает план, а не доказательство выполнения параллельного поиска. Выдача всегда пустая: `offers: []`, `connected: []`, сравнимых реальных предложений 0. В интерфейсе результат представлен сообщением; подробный план не показан.

### API тест / ZERO-COST VALIDATION

Отдельный компонент `ProviderSearch` отправляет запрос на `POST /api/validation/search`. Пользователь выбирает поставщиков и сетевой либо offline-режим.

Передаются дата начала, минимальное число ночей, 1–3 соседние даты, взрослые, возраста детей, аэропорты для авиационного теста и специальные коды Hotelbeds/Tourvisor. Не передаются все фильтры основной формы, распределение по номерам и группы split family. Гражданство в backend по умолчанию RU. Настройки основного блока источников не управляют этим отдельным тестовым выбором.

Тесты идут пакетами до трёх поставщиков параллельно. Результат — отдельные нормализованные компоненты FLIGHT/HOTEL/PACKAGE, а не связанная поездка. Если доступ отсутствует или запрос не удался, возвращается явно помеченная локальная MOCK-модель. На экране показываются до четырёх предложений каждого результата. Все результаты этого режима исключаются из экономического сравнения.

## 4. Куда сайт обращается

Все обращения к поставщикам выполняет backend. Ключи не должны передаваться в браузер.

| Источник | Реализованный запрос | Что получает сайт | Ограничение |
|---|---|---|---|
| Travelgate HotelX | POST `https://api.travelgate.com`, GraphQL search | Тестовые отельные тарифы HOTELTEST | Только client_demo, access 2, два фиксированных отеля ES284122 и BR1518; SYNTHETIC |
| Dida Content | GET `https://static-apiint.didatravel.com/api/v1/region/countries` | Справочник стран | Не цены и не наличие; вызывается кнопкой в разделе источников |
| Hotelbeds / HBX | POST `https://api.test.hotelbeds.com/hotel-api/1.0/hotels`; предусмотрен GET `/status` | Evaluation-тарифы выбранных кодов отелей | Нужны собственные key/secret и hotel codes; SYNTHETIC |
| Duffel | POST `https://api.duffel.com/air/offer_requests` | Тестовый перелёт туда/обратно на даты запроса | Только собственный duffel_test_ token; SYNTHETIC |
| RateHawk | POST `https://api-sandbox.ratehawk.com/api/b2b/v3/search/serp/region/` | Тестовые отельные тарифы региона | Собственные sandbox key ID/key; ограниченные тестовые регионы; SYNTHETIC |
| Tourvisor | GET `https://api.tourvisor.ru/search/api/v1/tours/search`, затем GET `/tours/search/{searchId}` | Начальный снимок пакетных результатов | Собственный JWT, trial mode, departure/country IDs; полноценный polling не реализован; реальность цены UNKNOWN |
| Open-Meteo | GET `https://api.open-meteo.com/v1/forecast` | Прогноз по координатам | Кнопка технической проверки; не подставляется в оценки всех карточек |
| Банк России | GET `https://www.cbr.ru/scripts/XML_daily.asp` через `/api/fx` | Справочные валютные курсы | Не банковский курс оплаты; не встроен в полный поиск поездки |

Для Dida PriceSearch существует код адаптера и разрешённый test endpoint, но общий поиск API-тестов его не вызывает. Dida rates в этом режиме возвращает MOCK. Публичный content account не считается доступом к тарифам.

Expedia Rapid, WebBeds, TBO, AviaCenter, Amadeus, SAMO, Juniper, Traveltek и Peakwork представлены в реестре, исследовательских материалах и/или заглушках. В текущем API-тесте сетевой тарифный поиск для них не реализован. Документация, SDK, OpenAPI и Postman сами по себе не дают работающего подключения. SAMO UI demo проверялся отдельно; это не SAMO API в поиске сайта.

### Публичные цены

`GET /api/public-prices` читает локальный файл `data/public_price_observations.json`. Он содержит три наблюдения с открытых страниц Level.Travel и Aviasales, датированные 19 сентября 2026 года. Автоматического обновления нет. Сайт не обращается к этим страницам при каждом поиске; ссылки открываются пользователем.

Эти суммы не являются ценой на заданную семью, не актуализированы и не участвуют в расчёте комплексной поездки.

### Сетевые ограничения

HTTP-клиент допускает только перечисленные read/search endpoints. Предусмотрены кэш, ограничение около одного запроса в секунду на поставщика в рамках процесса и повторы при сетевых ошибках, 429 и 5xx. Booking/payment operations отсутствуют.

## 5. Как сейчас рассчитывается стоимость

В демо базовая сумма вычисляется формулой из условной стоимости перелёта, количества человеко-ночей, числа номеров, коэффициента направления и дня недели. Возраст детей меняет условные коэффициенты. Это не правила детских тарифов реальных поставщиков.

Для пакета первая строка — «перелёт и проживание». Для самостоятельной/B2B/чартерной сборки отдельно формируются перелёт и проживание. Дополнительно модель добавляет:

- перелёт до gateway и обратно;
- ночёвки в gateway в обе стороны и питание на пересадках;
- багаж и обязательные сборы;
- трансферы, при разделении семьи — дополнительный трансфер;
- визы и разрешения;
- налоги отеля и курортные сборы;
- обязательную страховку;
- комиссии оплаты и конвертации;
- паром/автобус для отдельных встроенных направлений.

Все суммы в демо RUB. `totalRealCost` — сумма этих синтетических строк, несмотря на название поля. Это полная **модель** стоимости, а не реальная подтверждённая цена. Ночёвки, позиционирование и другие расходы заданы формулами, не результатами поиска.

В backend есть отдельный ценовой модуль: Decimal, исходная валюта, сумма после конвертации, источник/время курса, исключение повторного учёта включённых компонентов. Но он ещё не соединён с live endpoint в сборку всей поездки.

Сравнение реальной экономии допускается только для полного набора актуальных LIVE/REAL компонентов с подтверждённым `bookable: true`, одинаковым ключом сравнения и корректными валютными данными. Текущие API-тесты всегда `bookable: false`, поэтому такой расчёт не выполняется.

## 6. Что нужно уточнить в новом задании

1. **География и сценарии:** откуда искать, какие направления, аэропорты gateway, допустимы ли разные отели/даты/питание при сравнении.
2. **Источники:** какие разрешённые API подключить первыми; какие дают пакеты, перелёты, отели, трансферы и чартеры; где допустим только deeplink или ручное подтверждение.
3. **Точное размещение семьи:** состав каждого номера, возраста на даты поездки, детские кровати, вместимость, разные периоды проживания групп. Не рассчитывать реальную цену коэффициентом от тарифа на двоих.
4. **Полный цикл поиска:** справочники → поиск → ожидание завершения/pagination → нормализация → сборка маршрута → проверка цены и наличия. Задать лимиты запросов и времени.
5. **Строки стоимости:** что включено в пакет/тариф, что оплачивается отдельно, обязательные налоги на месте, багаж, питание, трансферы, gateway stay, страховка, комиссии и курс оплаты. Неизвестную сумму хранить как UNKNOWN, не 0.
6. **Подтверждение:** для каждого компонента хранить provider, offer/rate ID, параметры запроса, валюту, время получения, срок актуальности, статус наличия и ссылку/способ перепроверки.
7. **Маршрут:** оба направления, даты и часовые пояса сегментов, переходы между аэропортами, получение багажа, паспортный контроль, буферы, ночёвки и отдельные возвращения групп.
8. **Визы:** определить источник актуальных правил и проверять каждый паспорт и участок маршрута; отделить «требует проверки» от «разрешено».
9. **Качество данных:** откуда брать отели, питание, пляжи, погоду и отзывы; как сопоставлять одинаковый отель у разных поставщиков; что делать при отсутствии фактов.
10. **Выдача:** показывать отдельно подтверждённую полную цену, неполный расчёт с неизвестными расходами, публичное наблюдение и синтетическую модель. Только первый тип может доказывать экономию.

## 7. Основа для исправленного задания

> Соедини основную форму поиска с разрешёнными API поставщиков и единым backend pipeline. На входе используй даты, точный состав пассажиров, распределение по номерам и группам, VisaProfile и SearchSourceSettings. Для каждой включённой ветки выполни реальный поиск доступных компонентов, дождись завершения и обработай pagination. Нормализуй предложения, проверь совместимость дат, размещения и маршрута, затем собери полную стоимость с происхождением каждой строки. Неизвестные расходы и наличие не подменяй нулём или mock. Покажи пользователю состав стоимости, пробелы данных и способ актуализации. Sandbox/demo/mock оставь в отдельном режиме тестирования. До покупки API оцени доступные бесплатные источники, но не считай документацию или заглушку работающим поиском. Бронирование не выполнять.

## 8. Основные файлы реализации

- `frontend/app/page.tsx` — форма, режимы, карточки, сортировка и сравнение.
- `frontend/components/SearchSources.tsx` — настройки источников и позиционирования.
- `frontend/lib/search.ts` — локальные фильтры и синтетический расчёт.
- `frontend/components/ProviderSearch.tsx` — отдельная форма API-тестов.
- `backend/api/main.py` — endpoints и декларативный план live-поиска.
- `backend/providers/validation_search.py` — реальные test-запросы и MOCK fallback.
- `backend/providers/adapters.py` — адаптеры поставщиков.
- `backend/providers/http.py` — сетевой allowlist, кэш и лимиты.
- `backend/models/domain.py` — нормализованные сущности и настройки.
- `backend/pricing/engine.py` — сумма, конвертация и ограничения сравнения.
- `backend/visa/engine.py` — оценка визовых правил по доказательствам.
- `data/public_price_observations.json` — статические публичные наблюдения.
